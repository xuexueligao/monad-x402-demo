# 糯米起名铺产品与开发执行方案

版本：2026 年 10 月 17 日。项目暂名：糯米起名铺 / Nomi Works。执行基础：F:\出海项目\monad-x402-demo。

**先做一只会经营起名小店的猫：顾客给出项目描述，糯米收到订单款，在预算内购买一次 AI 工具，交付三个名字和宣传语，再把收入、工具支出和作品留在自己的工作记录里。**

首版的演示重点是“可爱的角色完成一笔真实可核验的服务交易”。全部链上付款使用 Monad 测试网测试 USDC。AI 模型在服务器运行；模型供应商的真实费用由开发者账户承担。完整 MVP 预计需要 10–15 人时，属于基于现有代码的工程估算；一个人应按 1–2 天安排。今天只有数小时，就按第 14 节先完成一笔订单的闭环。

本次已交付的素材是透明背景静态主视觉，1254 × 1254 像素。动作和功能实现仍按下文开发；不要把概念图当作已经完成的动画系统。

## 1 产品定位和第一批用户

第一批用户选择黑客松参赛者、独立开发者和正在起名的小项目作者。他们能提供具体任务，也容易当场判断结果是否有用。顾客购买的是“三个可比较的名字、一句宣传语和选择理由”，小猫提供记忆点和情绪反馈。

首版只经营一家店、一只猫、一项服务。操作者负责给猫配置工具、预算和服务说明；顾客负责提交需求、支付和选择结果。用预设工作流实现接单与执行，展示真实发生的步骤。第一版不把工作流描述成完全自主的通用智能体。

产品的主张可以写成：

> “给糯米一份委托。它会自己买工具，把作品和账单一起交给你。”

需要验证的两个假设：用户是否愿意使用起名结果；用户是否能理解并在意“猫有自己的工作账单”。可爱能促进第一次尝试，持续使用仍要依靠交付质量。

**首版完成的定义：**输入新需求后产生真实模型结果；顾客付款和猫购买工具各有一笔可核验的测试网交易；订单刷新后可恢复；同一订单重复点击不会重复收费；失败时能查明状态并执行退款；页面清楚标示测试网。

## 2 一次完整体验应该是什么样

顾客打开页面，看见糯米坐在一张小工作台后，面前有订单信封和一枚爪印章。它说：“今天想给什么起名字？”

以“给大学生找周末散步路线的小程序”为例：

1. 顾客输入项目描述，选择“轻松、好记、中文为主”，看到服务包含内容和 0.10 测试 USDC 的固定价格。
2. 顾客点击“请糯米起名”，连接钱包并签署本次付款授权。签名前能看到网络、代币、金额和收款方。
3. 服务端核验入账后，糯米把订单拿到工作台，显示：“收到委托，开始准备。”
4. 系统确认本单允许的工具支出为 0.02 测试 USDC，再调用起名工具。小票出现“起名工具：0.02 测试 USDC”，附交易入口。
5. 模型返回三个候选名字。糯米盖一个爪印，把作品卡推到前台。顾客可以复制文字、选一个喜欢的名字、下载卡片。
6. 工作小票显示“收到 0.10，工具支出 0.02，本单测试币余额增加 0.08”。这不是包含真实模型费用的利润。
7. 作品交付成功后，糯米得到一枚纪念饼干，播放一次庆祝动作。饼干是游戏反馈，不再额外扣款。

正常完成目标设为 15–40 秒，超过 45 秒显示仍在处理的具体步骤；这是体验目标，需实测后调整。链上等待、模型响应和故障恢复都可能拉长时间，不能用固定动画时长伪造完成。

## 3 小猫角色和视觉规范

### 3.1 糯米的设定

糯米是一只认真、有一点害羞的小店员。奶白毛、圆脸、短腿、短卷尾，眼睛为深巧克力色；淡紫三角围巾上的小星星缝线是固定识别点。工作道具使用薄荷绿订单信封、短铅笔和爪印章。

它偶尔歪头想一想，做完工作会把作品往前推一点。语言要短，能够说明状态：

| 场景 | 糯米的话 | 实际触发条件 |
| --- | --- | --- |
| 待接单 | 今天想给什么起名字？ | 没有运行中的订单 |
| 等待钱包 | 确认这份委托后，我就开工。 | 需要顾客签名 |
| 核实付款 | 正在确认这笔付款。 | 已提交，尚未核验 |
| 已收款 | 收到委托，开始准备。 | 入账回执核验成功 |
| 开始工作 | 让我认真想三个名字。 | 工具任务开始 |
| 交付 | 名字准备好了，看看你喜欢哪个。 | 结果合格且工具结算核验通过 |
| 状态待查 | 付款正在核实，请先不要重复支付。 | 结算超时或响应丢失 |
| 工具失败 | 这次没能完成，退款正在处理。 | 已确定失败并创建退款任务 |
| 休息 | 今日休息，明天再接新委托。 | 达到预算或订单上限 |

不要用余额不足触发哭泣、濒死或强迫充值。预算用完时让它喝水、睡觉、整理桌面，角色始终可爱、平静。

### 3.2 视觉令牌

| 名称 | 色值 | 用途 |
| --- | --- | --- |
| 云朵白 | #F8FAFC | 页面背景和留白 |
| 围巾紫 | #7765DA | 主按钮、当前步骤、少量强调 |
| 薄荷绿 | #DCF2E8 | 订单信封、工作区域背景 |
| 桃子粉 | #F6B7A5 | 腮红、饼干和少量装饰 |
| 墨蓝 | #2C3146 | 正文和账单金额 |
| 浅灰紫 | #E8E5F1 | 分隔线、次级表面 |

正文用微软雅黑 / PingFang SC / sans-serif 系统字体，英文店名可用 Trebuchet MS；标题 32–40px、正文 16px、账单 14–16px。标题字重 700，正文 400–500。首版不依赖外部字体下载。

金额、失败信息和关键按钮用深色文字或经过对比度验证的组合。粉色和薄荷绿主要用于底色；不要用浅色小字承担支付提示。所有按钮支持键盘，交互目标至少 44px；移动端表单输入字号至少 16px。

### 3.3 场景与动效

页面的主视觉是一张猫的工作台。左侧放糯米和当前状态，右侧是一张可填写的委托单，下方是一条真实事件组成的工作记录。把“可爱的工作台”作为唯一主要装饰，交易详情保持清楚、朴素。

首版使用现有透明图配 CSS 轻微呼吸、倾斜和移动，加信封、纸张、饼干等独立道具即可。静态图片无法独立眨眼或挥爪，不把这些动作写成已有能力。

完整动作素材按顺序补充：

| 动作 | 画面要求 | 何时使用 |
| --- | --- | --- |
| 招呼 | 当前主视觉 | 初次进入或待接单 |
| 打字 | 双爪落在小键盘上，保留围巾和脸型 | 工具处理期间 |
| 交付 | 双爪捧一张作品卡，微微前倾 | 成功交付一次 |
| 吃饼干 | 坐着抱一块小饼干，满足但克制 | 成功动画之后 |
| 休息 | 抱爪或蜷起睡觉 | 关闭营业或预算用完 |

首版可以先做“待接单、工作中、完成”三种场景状态；五张独立动作图作为下一轮素材任务。持续动画仅保留缓慢呼吸；收到订单和交付各播放一次反馈。开启减少动态效果时，使用静态图片和文字状态；音效默认关闭。

**设计取舍：**用工作台、订单纸和爪印收据承载信息，不做整屏相同卡片，也不用行情数字和币价图作为首页。小猫负责亲和力，账单负责解释真实行为。

## 4 第一项服务的输入与交付

服务名：“给项目起个好名字”。首版固定价格、固定交付范围，避免现场不断追加需求。

输入字段：

| 字段 | 约束 | 默认值 |
| --- | --- | --- |
| 项目做什么 | 必填，20–600 个字符 | 无 |
| 给谁用 | 可选，最多 80 个字符 | 普通用户 |
| 语言 | 中文、英文、双语三选一 | 中文 |
| 风格 | 可爱、专业、极简、脑洞四选一 | 可爱 |
| 避免的词 | 可选，最多 100 个字符 | 空 |
| 是否公开展示作品 | 明确勾选，默认关闭 | 不公开 |

服务器再次检查长度和选项。付款前冻结本单需求及其摘要；付款后改需求应创建新订单，不覆盖正在履行的订单。

每次交付必须包含三个不同候选。每个候选有名字、适用理由、一句宣传语；整单再给一个推荐及推荐原因。双语模式额外返回英文名，不能把翻译项当成新的候选凑数。

建议的结果结构：

这是展示格式的样例，不代表已经进行品牌检索。界面标注“创意建议，商标与域名可用性尚未核查”。不输出未经检索的“保证可注册”“域名可买”等结论。

模型适配层提供 generateNaming(brief)，返回经过服务端校验的结构化结果。候选恰好三个；名字彼此不同；字符串限定长度；拒绝混入付款地址、脚本或链接指令。优先使用服务商的结构化输出能力，不支持时执行 JSON 解析与校验。允许一次格式修复，计入真实模型调用上限，不向顾客增加收费。连续失败按失败订单处理，不把固定样例伪装成实时生成。

结果卡可复制文字，或使用浏览器 Canvas 导出 PNG。首版不再调用图片模型生成每单海报，避免新增长等待和费用。卡片带“糯米起名铺”、用户选择的名字和日期；分享时默认不带完整钱包地址和需求原文。

## 5 让它有想象力的五个机制

| 机制 | 用户看到什么 | 实现方式与阶段 |
| --- | --- | --- |
| 第一块自己挣来的饼干 | 第一笔成功交付后，糯米郑重收藏一张小票 | P0；用唯一完成事件触发一次动画 |
| 会留下痕迹的工作台 | 做完三单多一支铅笔，五单多一盆小植物 | P1；累计完成订单解锁装饰，退款订单不计 |
| 小猫给未来的自己写信 | 收工后生成一张“今天做了什么”的明信片 | P1；由真实订单摘要生成，先经用户选择分享 |
| 邻居工具店 | 糯米花钱请另一只角色做翻译或配图 | P2；先接入一个真实独立服务，分别展示收款与交付 |
| 带作品履历的猫 | 猫的技能来自已完成的作品和反馈 | P2；导出可核验付款记录与作品摘要，作品质量仍由评价体现 |

推荐的第二项服务是“把一个项目简介改写成三种介绍”，因为可以复用输入、结果卡和文本模型。翻译作为第三项。自动买卖资产、开放任意工具、复杂多人市场都不属于首版。

猫的个性可以影响措辞和装饰，不能改变报价、收款地址或预算。经营游戏的“成长”依据完成任务，不以钱包里的外部充值推算能力。

## 6 Monad 具体负责什么

| 部分 | 放在哪里 | 理由 |
| --- | --- | --- |
| 顾客向猫付款 | Monad 测试网 | 产生可独立核验的收入 |
| 猫向工具店付款 | Monad 测试网 | 产生可独立核验的工具支出 |
| AI 生成名字 | 服务端模型 API | 模型计算和密钥留在服务器 |
| 订单、预算、状态、访问权限 | 应用数据库与服务器 | 管理履约、并发和故障恢复 |
| 小猫表情、工作台、饼干 | 浏览器 | 根据可信状态呈现体验 |

x402 提供 HTTP 服务的付款协商与授权流程；facilitator 验证并提交结算交易。Monad 提供这些转账的链上执行与记录。两者的作用不同。官方已提供 Monad 的 x402 接入说明和测试网配置。[Monad x402 文档](https://docs.monad.xyz/guides/x402)、[x402 facilitator 文档](https://docs.x402.org/core-concepts/facilitator)。

选 Monad 是因为本项目面向其生态比赛，而且已有可以复用的支付代码。这种产品也可以在支持相关支付机制的其他网络实现。不要声称猫的智能只能运行在 Monad，或把官方性能指标当作本应用的实测成绩。

P0 使用固定价格的 x402 v2 exact 方案，不新增自定义合约。支付限额由服务端执行，因此是运营方控制的钱包和预算，不是链上不可绕过的托管规则。若具体赛题要求自定义合约或独立部署，先核对赛题；需要时把链上预算钱包放在后续范围，不能只为展示增加没有用途的合约。

## 7 钱包、价格和真实费用

### 7.1 四个角色

| 角色 | 用途 | 签名方式 |
| --- | --- | --- |
| 顾客钱包 | 支付 0.10 测试 USDC | 浏览器钱包由顾客确认 |
| 糯米钱包 | 收顾客款、付工具费 | 服务端专用测试私钥，经过预算检查 |
| 工具店收款地址 | 接收 0.02 测试 USDC | 只收款，不需要把私钥放进工具 HTTP 接口 |
| 运营补偿钱包 | 失败订单全额退款的准备金 | 操作者执行有金额与地址限制的退款命令 |

已有测试钱包可以按角色复用，但不能覆盖已有文件或重置余额。新增工具店、补偿钱包时，生成独立测试地址，脚本只输出公开地址。所有角色的地址必须可区分，避免把同一地址间的账面记数当作购买工具。

首版工具店由本项目自建，逻辑上与猫分开，使用另一个收款地址。它封装真实模型 API；演示中要明确说明这一点。接入独立第三方付费工具是 P2 的验证目标。

### 7.2 固定的首版参数

| 参数 | 首版值 |
| --- | --- |
| 顾客每单价格 | 0.10 测试 USDC，即 100000 最小单位 |
| 工具每单价格 | 0.02 测试 USDC，即 20000 最小单位 |
| 每单允许的付费工具任务 | 1 个 |
| 每日工具预算 | 0.20 测试 USDC，按 Asia/Shanghai 自然日计 |
| 每日新接单上限 | 10 单 |
| 模型调用上限 | 每单最多 2 次，包括一次格式修复；每日最多 20 次 |
| 同时执行的订单 | 1 单；其他订单进入可见队列 |
| 等待中的订单上限 | 3 单；满额时停止创建新报价 |
| 报价有效期 | 10 分钟；提交前再次检查 |
| 正常单测试币差额 | 0.08 测试 USDC，不称真实利润 |

所有金额以最小单位字符串保存、以 BigInt 计算，避免浮点误差。历史 /api/premium 示例继续使用 0.001 测试 USDC，新产品价格单独配置，不能改一个全局常量导致旧脚本付款金额变化。

单单账单显示收入、工具支出、退款以及交易状态；外部充值单独列为充值。用钱包总余额判断本单盈亏会混入充值、历史订单及退款，必须避免。

真实模型费用单独统计供应商返回的用量；取得真实单价后才能估算成本。尚无单价时显示“模型费用未计入”，不要把 0.08 测试 USDC 当利润。开发阶段可预留一小笔真实 API 测试预算，例如人民币 20–50 元，这是项目预算建议而非模型报价。服务商支持消费限额时再设置账户限额；应用侧仍执行调用次数与输出长度上限。

## 9 收款和买工具的具体实现

整体路径如下：

~~~mermaid
flowchart LR
  A["顾客提交委托"] --> B["确认顾客付款"]
  B --> C["订单入队"]
  C --> D["领取已承诺的预算预留"]
  D --> E["猫付费调用起名工具"]
  E --> F["校验结果与工具付款"]
  F --> G["交付作品和两张交易收据"]
  G --> H["记录完成事件并庆祝"]
  B -.状态不明.-> R["对账恢复"]
  E -.状态不明.-> R
  F -.确定失败.-> X["退款处理"]
~~~

### 9.1 顾客收款入口只接受委托

现有 x402 默认 authorization 流程会先执行业务处理函数，再进行结算。因此，不要直接把“猫花钱调用模型”塞进现有 /api/premium 的 handler。已安装 SDK 的执行顺序可以在 [Next 包实现](F:/出海项目/monad-x402-demo/node_modules/@x402/next/dist/esm/index.js:426) 中查看。

建议实现：

1. POST /api/orders 创建订单，保存冻结的需求、报价、访问会话、预期付款地址。报价前检查营业状态、模型配置、预算与队列名额。
2. 浏览器请求 POST /api/orders/{id}/pay，获得该订单的 x402 付款要求。
3. 顾客授权后重发请求。外层接口先检查订单访问权限和付款尝试状态；金额、代币、网络、收款方必须匹配服务端报价。
4. 在交给结算层前，持久化付款尝试及授权 nonce 与订单的绑定。数据库写入失败时拒绝继续结算。完整签名材料只存服务端受保护位置，不写入公开日志。
5. x402 包装的 handler 只确认“这份委托可以接受”，返回 orderId；此时不调用 AI、不展示收入已确认。
6. onAfterSettle 记录服务端得到的交易哈希和结算结果。worker 或对账步骤再核验链上成功回执、正确代币的 Transfer、from、to 和 amount。
7. 核验成功后，原子地将订单设为 queued。worker 从持久队列取得订单。
8. 如果 HTTP 响应丢失，浏览器通过订单查询恢复，不主动生成第二份付款授权。

x402 官方提供结算生命周期 hooks；本方案使用它们记录结算，但仍以本地已安装版本的类型和行为为准。[Lifecycle Hooks](https://docs.x402.org/advanced-concepts/lifecycle-hooks)。

特别注意：已安装版本的 onAfterSettle hook 异常不会撤销已经发生的链上付款。付款尝试必须事先落库，并有恢复路径；不能把“hook 成功写入”当成资金和数据库的原子事务。

### 9.2 猫购买一次起名工具

1. worker 领取一个已付款订单，在数据库事务中取得该单已有预算预留的执行权。该 0.02 测试 USDC 预算在报价阶段已经占用，收款后转为履约承诺；worker 不再重复预留一份。
2. 工具任务拥有固定 taskKey，由订单 ID 与服务版本生成。同一订单只能有一个对应的付费任务。
3. 请求固定白名单地址 POST /api/tools/name。初次获得 402 后，服务端检查报价，只有 network、asset、payTo、amount 和工具地址全部匹配才允许签名。
4. 签名由独立的 wallet 模块执行。模型不能读取私钥，模型输出也不能指定工具 URL、金额或收款地址。
5. 工具服务验证付款授权后调用模型，校验并暂存结果，再由 x402 结算工具费，成功响应包含结果与付款凭证。
6. worker 核验工具付款的真实回执，保存工具结果摘要，转换预算预留为已消费，进入 delivered。
7. 订单结果、完成事件和成长计数在一个数据库事务里提交；动画只响应这个唯一完成事件。

工具服务的模型结果按 taskKey 缓存。工具已结算但响应丢失时，通过受鉴权的恢复接口取回原结果和原凭证，不重新生成、不重新付款。格式修复在同一工具任务内进行，客户侧和猫侧均不增加报价。

两次转账是独立交易，不是一个原子合约。顾客款已到、工具失败时，需要应用安排退款；不能宣称协议自动完成整个业务的退款或履约保证。

### 9.3 预算限制必须在付款代码前执行

固定白名单至少包含工具 URL、收款地址、网络、代币和最大金额。自动跟随到其他域名的重定向应禁用；出现新报价或收款方变更时停止任务。

单笔、单日和并发限制同时生效。当天可用预算等于上限减去“当日已消费＋所有仍有效的未消费预留”；预算查询和预留必须在同一事务完成。两个并发请求不能同时读到同一份余额并都花出去。跨日保留尚未完成的预留，实际消费确认后记入消费当日；不能在零点清空未决承诺，再把同一额度给新订单。

P0 的限制属于服务端逻辑。需要链上强制限制时，再设计专用合约钱包或已验证的权限钱包，不在路演中把代码里的 if 判断称作链上规则。

## 10 订单状态、恢复与退款

业务状态和支付状态分开保存。支付记录至少区分 prepared、submitted、confirmed、unknown、failed；“签名已生成”和“钱已到账”是不同状态。

| 订单状态 | 进入条件 | 对用户显示 | 下一步 |
| --- | --- | --- | --- |
| awaiting_payment | 订单已创建 | 等待付款 | 签名或报价到期 |
| payment_pending | 已保存授权并开始结算 | 核实付款 | 查回执，不开放重付 |
| queued | 入账核验成功 | 已收款，等待开工 | worker 领取 |
| working | 已取得执行权和既有预算预留 | 工作中 | 工具执行与核验 |
| reconciling | 某笔支付状态不明 | 正在核实，请勿重复付款 | 恢复原尝试 |
| delivered | 合格结果和工具付款均已确认 | 展示作品、账单 | 记录反馈 |
| refund_pending | 订单确定不能交付，入账已确认 | 退款处理中 | 操作者执行退款 |
| refunded | 退款链上回执确认 | 已退款，显示凭证 | 终态 |
| cancelled | 未发生付款，报价失效或用户取消 | 委托已取消 | 可新建订单 |

处理要求：

- 顾客取消签名：保留未付款订单，可重试；不运行模型。
- 余额不足：显示需要的测试 USDC 数量与领币入口；不创建工具任务。
- 结算超时：设为 unknown / reconciling。根据原 nonce、付款尝试及链上事件查证，不自动签新授权。
- 链上成功但本地写入失败：通过事先保存的尝试、交易信息与 nonce 恢复关联；不按“数据库没有成功记录”判断没付款。
- 取到交易哈希也要核验币种、地址和金额；不能只信任浏览器传来的 success。
- 只有链上失败已确认，或原授权已到期且核验确未使用，才允许释放相应付款尝试并考虑新授权。无法证明时保留待核实。
- worker 重启：恢复持久订单；遇到进行中的支付先对账，不能把所有超时任务直接重新执行。
- 模型超时或格式连续不合格：确定是否已产生工具付款，再进入退款处理。缓存合格结果可以用于恢复，不能绕过未确认的结算。
- 付款之后停止营业：继续履行已确认付款的订单；预算承诺应在接单时预留，不能因后来新订单抢走预算而遗弃旧单。
- 单纯“我不喜欢这三个名字”在 P0 提供反馈入口，不承诺无限重做；可把一次免费文字微调放到 P1。

**退款策略：**技术原因无法交付时，退还顾客本单 0.10 测试 USDC。已发生的工具支出由运营补偿准备金承担，不能默认从退款里扣除。

P0 使用受保护的退款命令，由操作者检查订单后执行；界面诚实显示“退款处理中”，不要显示尚不存在的自动到账倒计时。退款的收款人只能是该订单经验证的付款地址，金额固定为尚未退还的应退额；独立的 refundKey 与数据库锁防止双退。退款发出后状态不明也要查原交易，不盲目再转一次。

为了支持普通 ERC-20 退款交易，补偿钱包需要测试 USDC 和测试 MON。正常 x402 流程的代付 gas 能力不能被当成所有退款转账都无需 gas 的保证。退款由补偿地址发出时，在账单注明来源。

## 11 数据结构与权限

### 11.1 最小持久数据

| 表 | 关键字段 | 核心约束 |
| --- | --- | --- |
| orders | id、sessionId、buyerAddress、brief、briefHash、quoteVersion、priceAtomic、state、result、createdAt | 需求付款后不可变；结果私有 |
| payment_attempts | id、orderId、kind、network、asset、from、to、amount、nonce、validBefore、status、txHash、logIndex | 授权 nonce 唯一绑定；一笔已确认转账不可认领给多单 |
| tool_jobs | taskKey、orderId、serviceVersion、state、result、usage、leaseUntil、leaseOwner | taskKey 唯一；结果缓存；短事务领取执行权 |
| budget_reservations | id、orderId、reservedDay、consumedDay、amount、status、expiresAt | 预留、消费和释放都具备唯一事件 |
| order_events | id、orderId、type、payload、createdAt | 完成、退款等事件有唯一键；不存密钥 |
| sessions | idHash、createdAt、expiresAt | 服务端持久会话；不把完整令牌存公开输出 |

钱包余额通过链上读取，业务账单通过已核验的支付记录生成，不维护一个可以随意加减的前端余额作为证据。

授权唯一标识使用 network＋asset＋payer＋nonce；链上已认领事件用 network＋txHash＋logIndex 唯一约束。EIP-3009 授权本身不包含应用订单正文，订单归属由受鉴权的请求和服务端映射确定，不能把普通 orderId 当作链上签名天然覆盖的字段。

数据库使用 WAL 和 busy timeout，短事务内进行状态条件更新。worker 执行租约建议 120 秒，模型单次请求超时建议 25 秒；不要在等待模型或 RPC 时持有数据库写事务。租约过期后的恢复仍受付款状态约束。

创建报价时原子预留容量及 0.02 测试 USDC 工具预算，付款提交后转换为待结算预留，收到款后变为履约承诺。正常报价 10 分钟过期；已经提交支付的预留不能仅凭时钟超时释放，须先解决支付状态。限制同一会话的未付款订单数量与创建频率，避免随意占满全部容量。

### 11.2 接口边界

顾客通过服务器设置的随机 HttpOnly 会话 cookie 访问自己创建的订单；生产环境使用 HTTPS、Secure、SameSite，并检查变更请求的 Origin。订单 ID 不是访问凭证。钱包地址是付款身份，不能靠提交一个地址就读取别人的订单。

P0 在同一浏览器恢复订单。跨设备恢复需要增加经验证的钱包登录或单独的恢复凭证，放到 P1。

公开的 /api/pet 只返回营业状态、匿名统计及允许公开的收款地址，不返回需求原文、完整模型结果、付款授权或内部错误。公开作品必须由顾客单独同意；默认关闭。

运营接口和 worker 接口用独立的高熵服务端 token 保护，并限制调用来源。该 token 不进入浏览器、不复用顾客 cookie。请求体设置上限；所有结果文本作为普通文字渲染，避免执行模型返回的 HTML。

P0 只接收文本。模型收到的是“待处理的用户描述”，不能因为描述中出现“转账到这个地址”等句子就取得支付权限。

scripts/
  nomi-worker.mjs                    请求内部 tick 的常驻循环
  setup-nomi.mjs                     无覆盖地准备本地数据与测试角色
  refund-nomi.mjs                    固定订单退款入口
  verify-nomi.mjs                    完整测试网订单核验
  verify-nomi-browser.mjs            界面与刷新恢复核验
public/nomi/

~~~

服务端模块不能被客户端组件导入。需要给页面的配置用显式白名单导出。共享类型不能顺便导入 wallet 模块。环境变量名中，私钥、模型 API key、worker token 不使用 NEXT_PUBLIC_ 前缀。

建议环境配置如下，值仅为字段说明：

~~~dotenv

OPERATOR_PRIVATE_KEY=补偿钱包专用测试私钥

OPERATOR_TOKEN=另一个高熵随机值
LLM_BASE_URL=已选择模型服务的API地址
LLM_API_KEY=服务端密钥

~~~

已有 PAY_TO_ADDRESS 保留给支付诊断。首版实现时选择一个实际可调用的文本模型和固定 API 适配器，先跑一次不收顾客款的模型预检，这次调用仍计入真实 API 费用；模型供应商尚未指定，不能把任何示例模型 ID 当作已确认可用。缺少配置时提供可操作的说明并关闭付费接单，不展示假生成。

Node worker 通过本地内部 HTTP 入口调用业务逻辑，避免额外引入 TypeScript 运行器。worker 的启动脚本包含退避和退出处理；单次 tick 等待其任务结束后再发下一次。它不依赖浏览器开启，也不使用 HTTP 响应结束后不受管理的后台 Promise。

## 14 开发任务与今天的安排

以下时间是熟悉 TypeScript 与钱包开发者的估算，包含现有支付代码可用这一前提。只有全部完成门槛满足，才能称为完成；不能因达到时间预算就用模拟状态补齐链路。

1. 前 30 分钟完成 A，明确模型和钱包是否可用。
2. 优先做 B、C 的最窄路径：创建一单、真实付款、可刷新查询。先保留简单文字界面。

4. 用现成角色图完成 E 的核心工作台；把动画、下载卡片和成长装饰放在支付与恢复之后。
5. 留最后一小时验证重复点击、付款取消、模型失败、状态待查，并试跑一次退款。完整画面录制至少一遍。

如果六小时内第二笔付款或恢复尚未完成，演示中明确列出已完成部分与下一步，不把直接调用模型的普通付款页面描述成猫已完成付费采购。可压缩装饰、反馈按钮、日记、更多动作；顾客金额正确、密钥隔离、重复扣款保护和真实状态必须保留。

## 15 验收矩阵与验证命令

只测试重要行为与风险，不为每个简单组件增加实现细节镜像测试。

| 场景 | 操作 | 必须得到的证据 |
| --- | --- | --- |
| 正常订单 | 用新需求完成一次付款与交付 | 真模型结果；两笔正确 Transfer；订单终态；金额差额 |
| 无钱包 | 点击起名 | 清楚提示安装或使用合适浏览器，没有请求模型 |
| 取消签名 | 拒绝钱包弹窗，再重试 | 第一次无收入、无工具任务；第二次可继续 |
| 钱包切换 | 创建后更换账户或链 | 重新校验身份与链；不能把另一账户的钱误记 |
| 测试币不足 | 余额低于报价 | 无已付款状态，无模型调用，提供领币说明 |
| 非法付款 | 错代币、金额、收款方或网络 | 服务端拒绝，未交付付费结果 |
| 连点两次 | 并发请求同一付款入口 | 至多一份有效结算与一个任务 |
| 已付款刷新 | 付款后刷新、关闭再打开 | 原订单恢复，读取不扣款 |
| 入账响应丢失 | 结算后断开响应 | 对账找回原交易，不产生第二笔顾客款 |
| 工具响应丢失 | 工具结算后中断 HTTP | 原 taskKey 找回结果与凭证，工具仅收费一次 |
| 模型失败 | 让模型超时或连续返回无效结构 | 不显示样例成功；进入退款处理并可核验退款 |
| 报价被篡改 | 修改工具返回的金额或地址 | 签名前拒绝，消费为零 |
| 并发预算 | 余量只够一单时同时提交两单 | 最多一单取得预算，另一单付款前被挡住 |
| 跨日预算 | 有未完成订单时跨过零点 | 未决预留继续占用额度，没有重复释放或超额接单 |
| worker 重启 | 在执行与对账阶段分别重启 | 无丢单；支付状态不明时停止重复执行 |
| 退款重试 | 重复提交同一退款命令 | 至多一笔应退额，未知状态先查证 |
| 隐私 | 第二个浏览器会话查询第一单 | 拒绝访问需求与结果 |
| 手机和动效 | 390px 与减少动态效果 | 无横向溢出，按钮可点，状态文字完整 |
| 真实预算 | 达到调用次数或营业限制 | 停止接受新付费订单，已收款单继续处理 |

## 16 部署方式与运行维护

P0 采用本地常驻运行，沿用 127.0.0.1:3143。Next 服务和 worker 分别运行，数据库位于持久目录；关掉整个主机不会继续工作，恢复后按数据库状态继续对账和任务。

需要给现场其他人访问时，再准备带 HTTPS 的单实例 Node 部署和持久磁盘。沿用 SQLite 的前提是单实例写入与可靠磁盘，不能直接部署到无持久磁盘、多副本自动扩容的环境并期待数据库一致。

公开测试前至少完成：恢复验证、预算限制、操作鉴权、备份与日志脱敏、用户结果访问控制、真实模型费用统计。备份包含 SQLite 数据库及正确的 WAL 一致性处理；密钥通过单独的秘密配置保管，不打包进展示材料。

首页展示准确的营业状态。worker 不可用、模型未配置、预算不足或接单队列已满时，报价接口和付款入口都要执行同样的判断。不能只禁用前端按钮而仍允许绕过页面付费。

最小运行指标：待核实付款数、已付款未完成订单数、模型失败率、今日调用次数、已预留与已消费工具预算。出现 unknown 或退款失败时，在经营者页面或本地终端给出可操作的订单编号，不自动给用户发送未授权的外部消息。

## 17 后续七天的顺序

| 阶段 | 要完成的事 | 成功标准 |
| --- | --- | --- |
| 第 1–2 天 | 完整 MVP 与关键故障恢复 | 一笔真实闭环、一次退款、一次重启恢复 |
| 第 3 天 | 五个动作素材与手机体验 | 表情统一，页面可用，减少动态效果可用 |
| 第 4 天 | 邀请 5 位目标用户尝试 | 记录是否选用名字和是否理解账单 |
| 第 5 天 | 优化命名质量与输入引导 | 降低无效输出，补足最常见的需求类型 |
| 第 6 天 | 第二项文本服务或工作台装饰 | 只做用户反馈最有价值的一项 |
| 第 7 天 | 复盘、决定继续方向 | 有实际作品使用反馈，再决定扩大服务 |

阶段顺序可按实际工时调整。未完成付款与恢复门槛时，优先补齐，不为了按日期增加新服务。

更远的版本可以让猫在“便宜但慢”和“贵一点但风格更合适”的工具中选择，再展示选择理由。只有出现多个真实可用工具与可验证报价后，才有必要让模型参与工具选择；决策结果仍要通过固定预算策略。

多猫社区最有价值的场景是角色之间交付真实服务：写作猫付费请翻译猫，翻译猫购买检查工具。先用两家真实服务验证协作，再考虑开放市场。钱包数量、交易笔数和装饰数量都不能代替交付价值。

## 18 两分钟路演脚本

0–20 秒：展示糯米。“这是糯米，它经营一家起名小店。顾客给它委托，它会在预算里购买工具，然后把作品和账单交回来。”

20–40 秒：输入现场真实项目描述。指出价格和交付范围，点击支付并由演示钱包确认。等待期间说明这是测试网。

40–75 秒：展示订单工作台。“这笔是顾客给它的收入；这笔是它向工具店支付的成本。两笔都有交易凭证。”等待状态必须来自真实订单。

75–100 秒：读出三个名字，选择一个，展示小猫交付与饼干反馈。让观众看到作品本身有可判断的质量。

100–120 秒：打开收据。“Monad 负责支付与账本，AI 在服务器工作。今天工具店由我们自建；下一步接入独立服务，让角色之间也能相互采购。”

现场只展示少量关键字段，完整地址和技术细节放在展开的凭证中。顾客付款与工具付款分别打开区块浏览器，不用一笔交易顶替两次行为。

准备一段已核验订单的录屏。现场网络故障时明确切换“录制演示”，画面标记录制时间和订单号，不能把录像当成现场实时交易。

评委可能问：

- “为什么用链？”——让角色的收款、采购和履历可以在应用之外核验；当前应用和模型仍有中心化运营部分。
- “它到底有多自主？”——当前在预设服务和预算内自动执行一次采购；没有开放式权限和无限自主花费。
- “猫真的赚到钱了吗？”——测试网展示资金流；真实商业利润还需要真实订单价格、模型费、链费和退款成本验证。
- “新意是什么？”——把角色的工作、成本、交付和成长放在同一段可理解的体验中，并使资金流可以检查。

提交材料包括项目说明、演示视频、运行步骤、两笔公开测试网凭证和架构图。实际报名资格、提交格式和评审要求以具体赛事当届规则为准。

## 19 怎么判断值得继续做

首轮先看 5 位目标用户能否完成任务，记录以下指标。数字是拟采用的验证门槛，不是已经获得的成绩：

- 至少 3 人选中一个候选，并说出愿意在哪里使用；如果只是夸猫可爱，需要继续改进服务。
- 至少 4 人能用自己的话解释两笔账单；不能理解时优先改文案与收据。
- 10 个验收订单中重复扣款为 0；成功订单的两笔金额和归属全部正确。
- 每个技术失败订单都能恢复交付或完成可核验退款。
- 跟踪从打开页面到开始填写、从填写到钱包确认的流失位置，区别需求问题与钱包门槛。
- 测试币支付不能证明真实付费意愿。后续可先访谈用户愿意支付的价格，再决定是否进行真实收费试验。

商业探索可以从创作者小工具、活动现场角色服务台、嵌入社区的品牌吉祥物三种方向中选一项。优先选择实际有重复需求的方向，不把“发宠物代币”当成收入来源。
