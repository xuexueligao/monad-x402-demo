# 糯米 AI 小猫产品与执行方案

> 历史方向：当前已改为奶龙形象的“骗龙夺宝”现场游戏。请以 [当前游戏方案](F:/出海项目/monad-x402-demo/docs/dragonbait/plan.md) 为准，本文件不再作为当前实施范围。

版本 3，2026 年 10 月 17 日。本版替代“糯米起名铺”；起名降为一种可能的任务，不再决定产品定位、入口、数据结构或收费方式。

具体实现、现有代码复用、依赖版本、接口、验收和 eventId 17 的参赛提交流程，按 [Mojo 结合实现方案](F:/出海项目/monad-x402-demo/docs/nomi/implementation-mojo.md) 执行。该方案已结合用户提供的 Mojo Agent Skill；本文件保留产品体验与能力方向。

**养一只有记忆、工具和专属钱包的小猫。你告诉它想办成什么，它自己规划工作；你允许它接外部委托时，它还能寻找机会、报价、交付和收取报酬。它的特长来自实际做过的事情。**

具体做什么，由用户目标、已接入的能力和出现的机会共同决定。任务入口始终开放；实际完成能力随工具接入增长。产品不预先给猫指定“起名师”“翻译员”或其他终身职业。

本版是产品设计和执行方案，下面的体验不是已实现能力。现有代码仍是 Monad x402 支付示例，角色图可继续使用。

## 1 核心体验

用户领养糯米后，可以自然地说：

> “下周要参加比赛，帮我把这个想法准备成能演示的东西。”

糯米理解已有材料与目标，列出缺少的信息，组合研究、创作、代码和文件能力。它可能查资料、画一张图、做一个页面、准备一份路演稿；每一步都留下真实成果。必要时，它从可用服务中选择付费工具，并说明用途和费用。

用户也可以说：

> “今天我没有事情交给你。你看看任务广场有没有合适的活，赚一点工具费。”

只有在主人已启用这个模式、费用和接单条件允许时，糯米才去查看实际发布的任务、判断匹配程度、报价或接单。任务不存在时就如实报告没有找到，不制造收入。

用户再次打开应用，应能看见它完成了什么、尝试过什么、还在等什么，以及为什么采取这些行动。

## 2 它具体可以做什么

下面是用来理解和验证能力组合的场景，不是固定业务菜单。

| 用户的目标 | 小猫可能采取的行动 | 最后交付 |
| --- | --- | --- |
| 给朋友一个特别的生日惊喜 | 了解朋友偏好，整理用户提供的照片，设计卡片或互动页面 | 定制卡片、祝福文字、可预览的小网页 |
| 把我的点子变成别人能看懂的产品 | 调研相关产品，提炼核心流程，生成视觉与页面，检查能否打开 | 带来源的简报、可运行原型、演示稿 |
| 这堆资料我明天要讲给别人听 | 阅读文件，提炼主线，找出处，组织表达，制作讲稿与演示文件 | 可编辑的讲稿、幻灯片或复习卡片 |
| 帮我把周末活动安排妥当 | 查地点和时间，比较方案，整理预算与人员分工 | 日程、备选方案、邀请草稿与物品清单 |
| 让这个旧项目重新有点意思 | 阅读已有内容，找可改善的地方，改文案、画面或交互 | 具体修改、前后对比与可检查结果 |
| 帮我把这一期内容做出来 | 从资料中找角度，形成脚本，配图并整理发布素材 | 文稿、配图、标题备选和排版文件 |
| 自己去挣下一次工具调用的钱 | 阅读真实任务，评估所需能力和成本，完成已接下的委托 | 顾客收到成果，猫获得实际报酬和评价 |
| 遇到自己不熟悉的问题 | 找到缺少的能力，查询可接入工具，或向其他服务采购 | 新工具的使用记录、协作交付或清楚的能力缺口 |

这些例子跨越生活、创作、研究、软件和经营。用户还可以提出未在表中出现的目标；系统尝试用现有能力组合处理，而不是提示“请选择已支持的业务类型”。

涉及发布、发送、购买、账户操作等行为时，执行用户已经设置的授权规则。用户可以预先授权明确范围内的自动动作，范围内无需每一步打断询问；新出现的费用或权限需求在发生前说明。

## 3 三种工作方式

### 用户交给它事情

输入一段自然语言，可附文件、链接和参考图。小猫理解期望成果，尽量利用已有上下文；只有缺少会改变结果的关键信息时才追问。

费用来源是用户给这项任务的预算。主人转给猫的钱属于拨款，不能记成猫靠外部工作获得的收入。

### 小猫主动提出有用的行动

用户可以启用某个长期目标，例如“帮我推进这个项目”或“帮我持续整理这个主题”。糯米结合任务历史和明确的计划，提出下一步，或执行已授权的周期工作。

“主动”必须有依据：用户指定的目标、到期事项、已连接数据中的变化或正在进行的任务。不能为了显得忙碌，每天生成没有用途的文件，也不能在没有后台运行环境时声称用户离线后仍在工作。

### 小猫自己接委托

用户启用“允许接活”，设置可用时间、预算与接单条件。糯米从真实任务来源挑选适合的机会；同一只猫可以做研究、设计、翻译或其他能够完成的工作。

首批任务来源是邀请体验者实际发布的委托。外部自由职业平台是否允许自动访问、报价和交付，需要逐个接入核实，不能默认任意平台都可自动接单。

如果只有团队自建的测试委托，标注“演示委托”。工具市场的存在不等于有人发布付费工作；需求获取与工具发现是两个独立问题。

## 4 什么会让用户愿意持续养它

**连续的记忆。**它记得用户已经说明的偏好、正在推进的项目和过去交付的版本。记忆可查看、修改、删除；每条重要记忆带来源和更新时间。一次猜测不能悄悄成为永久偏好。

**可以看见的工作过程。**读材料时抱着书，画图时拿画笔，写代码时面对小电脑，接单时背着信封。动作由真实工具事件驱动。用户点开就能看到文件、来源、预览和状态。

**逐渐形成的特长。**“擅长做演示”应有实际完成记录和用户评价。完成五次任务不意味着模型自动获得新的专业能力；新能力来自可用工具、可复用工作流程和经过验证的经验。

**自己的经营选择。**在用户给定条件下，比较工具的用途、价格和历史结果。一个免费的工具足够，就不必花钱；外包能提高交付质量且在预算内，可以说明理由后采购。

**有出处的小惊喜。**例如把某个项目的阶段成果整理成一张回顾卡，或发现用户一直整理的资料已经足够做一份小册子。惊喜来自真实积累，不能凭空编造用户经历。

一个理想的回家场景是：

> 糯米把三样东西摆在桌上：你交代的演示稿、一位顾客确认收到的翻译稿，以及购买工具留下的小票。它说：“今天我学会了把你的图表整理得更清楚。”

这是一段目标体验；交付、顾客、学习记录和付款都必须能点开查证。

## 5 角色和页面如何承载这些能力

小猫形象沿用现有素材：奶白绒毛、圆脸短腿、淡紫围巾、薄荷绿信封。保留这些稳定特征，职业道具随任务变化，不用固定店铺职业锁住它。

首页可以是“糯米的小房间”：

~~~text
┌───────────────────────────────────────────────────────────┐
│ 糯米                   当前任务 2        预算与账单        │
├──────────────────────────────┬────────────────────────────┤
│                              │ 今天想一起办成什么？        │
│         小猫的房间           │                            │
│                              │ [自然语言输入，支持附件]    │
│  书架    画板    工作电脑     │                            │
│  项目纪念品   正在处理的信封 │ [交给糯米]                 │
├──────────────────────────────┴────────────────────────────┤
│ 它正在做：阅读活动资料 → 设计画面 → 整理邀请页面           │
│ 最近带回来的成果：文件、图片、网页、顾客反馈               │
└───────────────────────────────────────────────────────────┘
~~~

输入框是主入口。可以展示几个灵感例子，但不要求用户先从固定服务列表选择。用户说“做活动邀请页”时，系统得到一个开放目标，而不是把它强行转换成命名订单。

房间中的物件是有内容的入口：书架打开资料和记忆，画板打开视觉作品，电脑打开正在进行的任务，信箱打开外部委托，账本打开真实收支。移动端将它们变成可读的列表入口，避免必须精准点击小物件。

动作首批制作待命、阅读、创作、等待、交付、休息。现有图是静态角色主视觉，不是完整动作集。动效不能替代状态文字；保留键盘操作和减少动态效果。未完成任务时不播放完成庆祝，余额不足时可以休息或提出预算调整，不制造悲伤和充值压力。

## 6 相关产品给我们的启发

决策问题：为希望有长期搭档、又对数字宠物有兴趣的用户，做一只能够完成开放任务的小猫，本轮需要判断“持续关系、可见工作与经济行为”是否值得保留和投入。若用户只关心一次性结果、不再回来看猫，应减少养成比重，继续验证工作价值。

这轮仅查阅官方公开资料，没有实际操作这些产品，也没有验证其成功率、用户规模或商业数据。

| 参照 | 官方材料可支持的事实 | 对本项目的启发 |
| --- | --- | --- |
| Manus | 功能页列出研究、网站、媒体创作、自动化和连接工具等能力 | 通用任务能力本身已有成熟竞争，不能仅靠扩大功能列表吸引用户 |
| Pippin | 官方仓库描述目标、角色、工具、记忆及活动选择机制 | 数字角色可以围绕长期目标行动，角色与记忆需要影响真实使用体验 |
| Virtuals 的 ACP | 官方白皮书把 ACP 描述为智能体间协调交易与交付的商业协议层 | 智能体经济需要任务、交付和交易关系，仅有钱包还不足以形成市场 |

来源：[Manus 功能](https://manus.im/features)、[Pippin 官方仓库](https://github.com/pippinlovesyou/pippin)、[Virtuals 官方白皮书](https://whitepaper.virtuals.io/)。

推导出的候选方向是：围绕同一只持续存在的猫，把作品、记忆、技能和账单连接起来。这是产品假设，不是已经证实的竞争优势。对应的验证是观察用户在完成第一项任务后，是否愿意把不同类型的第二项任务也交给同一只猫，以及记忆是否实际减少了重复解释。

## 7 Monad 在开放任务中扮演什么角色

Monad 用来记录真正需要结算的行为：顾客付给猫的委托款、猫购买工具的费用、采购其他智能体服务的款项以及退款。不是每次思考、每个动作和每个免费工具调用都要上链。

x402 提供 HTTP 服务的付款协商和执行路径，Monad 官方已有相关接入说明。[Monad x402 文档](https://docs.monad.xyz/guides/x402)。

开放任务让钱包的用途更自然：小猫发现当前任务需要某种工具，比较可用服务，在任务预算内购买，再把成果与成本一起交回来。工具费用随任务而变化，不再规定所有订单都收 0.10、都花 0.02，也不强求每次恰好发生两笔转账。

工具发现可以评估 x402 Bazaar：官方文档描述了查询服务能力、价格和输入输出结构的机制。但只有支持该扩展的 facilitator 提供相应发现接口，服务也可能属于其他网络。[Bazaar 文档](https://docs.x402.org/extensions/bazaar)。当前 Monad facilitator 的发现能力与可用服务清单尚未实测；不能假定目录中的所有工具接受 Monad 测试币。

首轮可以维护一个经过验证、可继续增加的工具注册表。接入新工具要增加它的能力描述和适配器，不应要求重新设计产品任务类型。

主人任务、外部订单和工具采购分开记账。测试币是测试结算；真实模型费用由实际供应商账户承担。未完成需求验证前，不把“能自主付款”描述为“能稳定赚钱”。

## 8 用户应该设置什么

任务内容用自然语言表达，不设业务白名单。用户掌握以下实际控制：

- 想完成什么，最终希望得到什么成果。
- 最晚什么时候需要，哪些偏好值得记住。
- 这次可使用的费用，以及是否允许在既定预算内选择付费工具。
- 是否允许接外部委托或围绕某个长期目标主动工作。
- 已授权哪些账户、文件、发布或发送操作。

这些设置可以长期保存并按任务继承，避免每次从头配置。普通研究、草稿和本地文件生成可按已有授权自动执行。超出已有权限或费用约定时，系统在动作发生前提出具体需要。

“任务不预设类别”和“工具执行有权限依据”可以同时成立。面向用户表达为“告诉它目标和你愿意投入多少”，而不是展示一大页技术限制。

## 9 从开放目标到可执行任务

处理过程采用循环，而非固定单一流水线：

~~~text
理解目标与已有资料
    ↓
寻找能完成目标的能力
    ↓
制定步骤、成果要求与费用估计
    ↓
执行一个步骤并保存真实结果
    ↓
检查结果是否满足目标
    ├─ 满足：交付并保存可复用经验
    └─ 不满足：修改步骤、补充工具或报告实际缺口
~~~

首版规划器输出结构化计划，至少包括目标、成果要求、步骤及依赖、工具需求、费用估计、可自动执行的动作和需要补充的信息。

计划允许修改，但有版本记录。新计划超出已约定预算或引入新外部动作时重新核对授权；不能让模型通过改写计划绕开已有条件。

推荐的核心对象：

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| Task | goal、context、attachments、deliverables、acceptance、budget、owner | 开放目标与用户期望 |
| Plan | version、steps、dependencies、estimatedCost | 可以修订的执行计划 |
| Tool | id、description、inputSchema、outputSchema、priceQuote、permissions、availability | 已验证的工具能力 |
| Execution | taskId、stepId、toolId、status、attempt、resultRef | 真实运行记录与恢复 |
| Artifact | type、path、version、preview、sources、validation | 文件、图片、网页或其他交付物 |
| Memory | content、source、scope、confidence、updatedAt | 用户可控制的长期上下文 |
| Opportunity | source、requester、goal、deliverables、compensation、deadline、status | 外部真实委托 |
| Payment | purpose、quote、payer、receiver、nonce、status、txHash | 收入、拨款、工具费与退款 |

Task 不使用 name_job、translate_job、poster_job 这样的封闭业务枚举。工具有明确输入输出和权限，任务目标保持自由描述。

交付验证随成果变化：报告检查来源与覆盖范围；图片检查文件和尺寸及与需求的符合度；网页在隔离环境启动并检查关键交互；文档检查可打开性与主要内容。主观质量需要用户反馈，不能仅凭模型自评宣布优秀，链上付款也不证明作品质量。

## 10 第一轮接入哪些底层能力

先完成一组能够跨任务组合的能力。它们是执行积木，数量可增加，不是限定小猫职业的菜单。

| 能力 | 可支持的任务 | 真实输出要求 |
| --- | --- | --- |
| 搜索与网页读取 | 调研、活动准备、比较、事实核查 | 链接、来源内容与获取时间 |
| 文件读取与文字处理 | 学习、翻译、归纳、创作、数据整理 | 可追溯的文本或结构化数据 |
| 图片生成与编辑 | 卡片、插图、海报、产品概念 | 实际图片文件及可查看预览 |
| 文档与页面组装 | 报告、清单、讲稿、展示页面 | 可打开或可运行的成果 |
| 隔离代码执行与预览 | 小工具、网页、格式转换 | 限定环境中的运行结果与检查 |
| 工具采购与协作 | 缺少能力时购买服务 | 服务报价、实际结果与结算记录 |

这里没有声称现有项目已经具备这些能力。每个适配器接入后先用独立小任务证明能够运行，再开放给规划器选择。一个能力不可用时，准确说明缺失，并继续可完成的部分；不把假的占位结果交给用户。

“学会新技能”可以对应三种真实变化：新接入一个工具；把成功步骤保存成可复用流程；从明确反馈中保存一个有来源的偏好。普通经验积累不自动等于重新训练模型。

## 11 现有项目如何修改

本次再次读取了项目 AGENTS.md、package.json、支付路由和网络配置。现有依赖仍为 Next 16.4.2、React 19.3.1、viem 2.57.7、x402 2.28.0；现有 /api/premium 返回固定内容，不是通用任务引擎。

可复用：

- 浏览器钱包连接、切链和 x402 客户端。
- 测试网配置、支付核验及既有验证脚本。
- 糯米角色图与视觉配色。
- 之前方案中关于持久付款尝试、重复扣款防护和恢复的工程要求。

需要替换的设计：

| 原设计 | 本版设计 |
| --- | --- |
| 起名表单 | 自然语言目标与附件 |
| 固定名字结果 | 根据目标生成多种成果 |
| 每单固定价格 | 按计划报价或使用用户给定预算 |
| 固定一次工具调用 | 可修订的多步骤执行 |
| 固定职业与技能 | 工具注册表、经验与真实作品履历 |
| 每单固定两笔转账 | 根据实际采购产生零笔、一笔或多笔支出 |
| 只接顾客订单 | 主人委托、主动目标和外部委托 |

拟新增模块，均为计划位置：

~~~text
src/server/nomi/
  tasks.ts              目标、成果要求与状态
  planner.ts            步骤生成与计划修订
  executor.ts           步骤执行、恢复与依赖
  tool-registry.ts      能力描述、可用性与适配
  tools/                已接入工具的实现
  artifacts.ts          成果文件与验证记录
  memory.ts             可查看、修改和删除的记忆
  opportunities.ts      外部委托来源与选择
  budget.ts             按任务和用户授权管理费用
  payments.ts           x402 与链上回执核验
  db.ts                 持久数据
src/app/
  page.tsx              小猫房间与开放目标入口
  tasks/[id]/page.tsx    计划、执行记录与成果
  memory/page.tsx        偏好与项目记忆
  ledger/page.tsx        收支与凭证
  api/tasks/...         创建、读取、修订与执行
  api/tools/...         工具描述和可用性
~~~

继续保留原 /api/premium 的 0.001 测试 USDC 支付示例作为诊断。新业务不能通过修改一个全局价格常量破坏旧验证。

首版可以沿用单实例 Next、持久数据库和后台 worker。执行生成代码时另用隔离环境，绝不把拥有钱包私钥的应用进程同时当作任意生成代码的运行沙箱。是否复用已有 agent runtime，在确认可用接口后决定，不为开放任务预先重建一个完整通用平台。

## 12 资金与执行恢复仍然需要成立

任务开放后，不能把每一项工具消费都预写为固定金额。规划时估算，执行前获取并校验实际报价，在已授权预算中原子预留；付款确认后计入已消费，失败或取消按可核验状态释放。

同一任务可以存在多个步骤，每个可收费步骤具有稳定的执行 ID 和付款尝试 ID。重试、刷新、进程重启不能自动重复付款。支付状态不明时先对账，只有证明原尝试没有成功且不会再被结算，才创建新的付款尝试。

沿用当前 x402 时，注意默认流程可能在 handler 运行后才结算。外部顾客收款入口只接受委托并记录付款，确认入账后再让 worker 执行需要垫付的采购。不能因用户已经签名就认为资金已到账。

预付款、客户验收和自动付款是不同业务步骤。P0 可采用报价后预付、技术失败可退款的方式；人工验收或托管合约需要另行实现，不能把 x402 直接付款称作自动托管。

不同目的的支出区分为用户任务成本、外部委托履约成本和主动探索预算。主人充值不计入营业收入；不同模型供应商的真实费用与测试币结算分开核算。

这些是让开放任务可靠运行的基础，不是给小猫预先规定它只能做什么工作。

## 13 第一场演示应证明什么

用同一只猫、同一个输入框完成三种不同目标，建议选择：

1. “帮我研究一个参赛想法，整理成带来源的简报。”
2. “把这些资料做成一张生日卡片。”
3. “把刚才的想法做成一个可打开的介绍页面。”

三者依赖同一套规划与工具执行能力，不分别写成三条固定业务分支。再现场输入一项开发前没预设的任务，例如“把这段活动说明变成可勾选的准备清单”，检查是否能组合已有能力处理。

接着演示一次真实工具采购。能使用免费能力完成的任务不为了上链而额外购买工具。付费服务自建时明确标注自建；使用测试网时持续标明测试币。

最后由另一位体验者发布一份真实委托，小猫在启用接单的条件下评估并完成它，展示报价、成果、评价和收款。没有实际外部委托时，只展示已完成的主人任务和工具采购，不把测试数据称作经营收入。

路演中最有吸引力的片段应是：同一只猫面对不同目标，采取不同步骤，交出不同形态的成果，并记得用户此前表达过的偏好。

## 14 开发顺序与完成门槛

不沿用上一版单项服务的 10–15 人时估算。下表描述产品能力演进；本次参赛版本的具体研发阶段与工作量，以 [Mojo 结合实现方案](F:/出海项目/monad-x402-demo/docs/nomi/implementation-mojo.md) 第 12 节为准，约 24–42 人时，外部账户和审核等待另算。

| 阶段 | 具体工作 | 通过后才能进入下一阶段的证据 |
| --- | --- | --- |
| A 能力探测 | 核对模型、搜索、图片、文件与执行环境的实际可用接口 | 每个准备启用的工具有真实输入输出样本 |
| B 开放目标闭环 | Task、Plan、Executor、成果与持久状态 | 相同入口完成两种不同目标，刷新能恢复 |
| C 扩展与检查 | 追加工具适配、成果校验、重试和能力缺口反馈 | 第三种目标及一个未预设目标可运行，无业务枚举分支 |
| D 小猫与记忆 | 房间、状态、可编辑记忆、作品历史 | 第二个任务正确使用用户确认的偏好，并可删除 |
| E 工具采购 | 按步骤报价、预算、x402、真实凭证与恢复 | 一次真实采购，重复调用不重复扣款 |
| F 外部委托 | 任务来源、评估、报价、交付、评价和收款 | 另一位用户发布并验收实际成果 |
| G 长期目标 | 任务调度、后台恢复、主动提案 | 在明确授权的目标内运行，离线能力与部署条件相符 |

今天优先做 A 与 B：先证明它能理解不同目标并组合工具，不再把大部分时间花在固定起名服务的支付表单。已有角色图可以直接用于极简工作台。支付与经营接在真实任务执行能力之后。

这不是承诺一天内做出所有能力。每个阶段保持开放目标的数据与界面结构，按已验证的工具逐步扩展；可以少接工具，不能把尚未接入的能力伪装成可用。

## 15 验收与产品验证

| 要验证的事情 | 观察方法 | 失败后的调整 |
| --- | --- | --- |
| 不被固定职业锁住 | 同一输入框提出四种不同目标 | 检查任务层是否写死分类与结果结构 |
| 有真实交付能力 | 打开生成文件，运行网页，抽查来源 | 先改善对应工具与验证器 |
| 能适应中途改变 | 改一个偏好或交付格式 | 修订计划，保留成果版本，重新核对费用 |
| 记忆有帮助 | 下一项任务沿用已确认偏好 | 调整记忆提取与可见控制 |
| 成长有依据 | 点击技能或纪念物，能追到作品和反馈 | 去掉没有证据的能力等级 |
| 接活有真实需求 | 有实际发布者、需求、交付和验收 | 优先找真实任务来源，不制造虚假订单 |
| 钱包行为可信 | 校验每笔用途、金额、地址与回执 | 补足付款恢复和账单关联 |
| 失败不会假装完成 | 工具不可用、额度不足、返回错误 | 给出实际缺口和可继续完成的部分 |
| 恢复不会重扣款 | 中断进程、丢失响应、重复提交 | 维护稳定步骤 ID、付款状态和结果缓存 |
| 主动行为有依据 | 关闭与开启长期目标后观察动作 | 修正触发规则和授权继承 |
| 任务资料隔离 | 两个会话交叉读取成果和记忆 | 修正访问控制 |
| 用户愿意继续养它 | 首次交付后，观察第二次不同目标的主动使用 | 区分结果质量、人格体验和需求频次问题 |

试用时同时关注“事情有没有办成”和“是否愿意继续交给同一只猫”。不要仅统计点了多少次猫，也不要把测试币收入当成付费意愿证据。
