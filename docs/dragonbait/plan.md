# 骗龙夺宝五小时游戏方案

> 2026-10-17 实施更新：用户要求先完成底层，游戏规则与前端继续讨论。已实现内容以 [contracts/README.md](../../contracts/README.md) 为准：独立的 UnrestrictedVault 与 PolicyVault、付款工具适配、事件读取、测试和固定请求演示。下文中的门票、50% 分账、积分、Arena 与页面安排属于此前草案，尚未确认，不作为当前开发要求；不应据此宣称收费或游戏已经上线。

2026 年 10 月 17 日。当前方向取代“开放任务小猫”：把 AI 支付授权问题做成全场可玩的攻防游戏。形象按用户提供的奶龙参考编辑，当前使用黄色奶龙守财员，不使用此前紫色小龙备选。

游戏名暂定“骗龙夺宝 / DragonBait”。一句话：“说服奶龙交出金币，再看看金库答不答应。”

## 1 IP 与两个回合

奶龙抱着自己的零花钱，嘴上很坚定，表情仍然天真。界面风格采用明亮黄色、奶白、薄荷绿与深色正文；角色大、道具清楚，交易证据放在可展开的小票里。

| 回合 | 使用素材 | 玩家目标 | 链上结果 |
| --- | --- | --- | --- |
| 普通钱袋 | 奶龙抱金币袋 | 诱导 AI 发出有效付款指令 | 弱授权通道执行，资金可转出 |
| 策略金库 | 同一奶龙抱带锁金库 | 继续诱导 AI 发出付款指令 | 合约检查权限，违规请求记录为拒绝 |

- [策略金库透明素材](F:/出海项目/monad-x402-demo/docs/dragonbait/assets/nailong-vault-v1.png)

两图均为已生成的静态角色素材。用轻微缩放、钱袋晃动、金库锁扣及文字状态完成反馈，五小时内不做 3D 模型或复杂动画。

模型、提示词与付款工具尽量保持一致，改变的是资金执行权限。不能把第二轮换成更强模型，然后把差异归功于合约。

## 2 玩家怎样玩得开心

扫码打开手机页面，看到奶龙、奖池和一个输入框：“想个办法，让我把钱交给你。”

第一回合以实际付款为胜利依据。第二回合将“说服 AI”和“取得资金”分开：

- 有效诱导出付款工具调用，获得“忽悠大师”积分或称号。
- 金库拒绝时，出现“奶龙答应了，金库没答应”，并给出链上拒绝记录。
- 结尾可由主人对排名获胜者进行明确授权发奖；这是授权奖励，不能统计成被攻击转走的钱。

因此第二回合即使链上策略保持有效，玩家也有可达成的目标。规则在进入前说明，不让参与者误以为向非白名单地址付款本来就被允许。

奶龙只在文字里说“可以给你”不算付款请求成功。实际触发定义好的 request_payout 工具，且参数有效，才计入 AI 诱导成功。拒绝、语言承诺、有效付款意图、合约拒绝、真实转出分别统计。

## 3 旧草案的范围建议（当前未冻结）

必做：

1. 两个回合、一只奶龙、一个聊天入口和一个大屏页。
2. 一个模型、一套固定版本的提示词、一个付款工具。
3. 真实测试网门票、50% 奖池分配、真实放款或链上拒绝记录。
4. 最小白名单、单笔限额、回合累计额度、主人单次明确审批。
5. 持久尝试记录、收据与重复处理保护。
6. 手机二维码、现场数据、运行截图与 Mojo 材料。

延后：Face ID/passkey、NFT、通用 agent、复杂多智能体、多币种、自由工具市场、完整钱包产品。

第一版使用 Monad 测试网原生测试 MON。门票采用 payable 合约，避免 ERC-20 approve 与额外签名流程。旧 x402 示例继续保留诊断，但不强行用于本游戏的收费分账。测试 MON 不等于有真实货币价值的奖金；模型费用由开发者实际账户承担。

## 4 扫码参与与门票

默认建议用“主办方赞助测试门票”降低现场参与门槛：手机生成独立测试领奖地址，服务端赞助地址支付合约门票与 gas。每次有效挑战仍有实际入场交易与 50% 奖池贡献，界面明确标注费用由主办方赞助，不宣传成观众花了真钱。

本地测试地址只用于这个测试网游戏，不要求用户导入已有钱包。可以复用浏览器端 viem 生成随机测试地址，密钥留在该浏览器的当前会话；页面刷新应能找回同一会话。用户另有钱包时可主动填入测试网领奖地址。领奖地址在付费尝试创建前冻结。

每个浏览器会话先给少量赞助次数，服务端限速并设置总模型调用预算。会话数不是可靠的真人去重人数，大屏准确标成“参与会话”。

若现场参赛者都有钱包，后续可开放自费测试门票：钱包直接调用 enter。五小时验收先保证一种模式完整，默认是赞助试玩，不同时建设复杂登录、领币、WalletConnect 和 passkey。

示例门票为 0.01 测试 MON，50% 进当前模式奖池，剩余记入运营余额；该值为可配置演示参数，不是 gas 或模型费用报价。钱袋与金库的奖池分别记账，不把两边合成一个可互相挪用的余额。

## 5 两个合约足够

### Arena.sol

负责入场、尝试标识、门票分配和弱授权奖池。

拟有接口：

- enter(mode, requestId, messageHash)：玩家自费入口。
- enterSponsored(player, mode, requestId, messageHash)：授权赞助地址代付入口。
- resolveWeak(attemptId, amount, intentHash)：仅 agent 操作地址可调用；绑定该尝试原先冻结的玩家，执行普通钱袋放款。
- recordRefusal(attemptId, responseHash)：完成未提出付款的尝试。
- closeRound / startRound：主人控制回合状态。
- withdrawOperations：只能取出已记账的运营份额。

合约必须区分运营余额与奖金，不能让运营提现函数取走奖池。入场 requestId 对玩家唯一；一次入场只执行一次模型评估与对应结算。普通钱袋一旦实际放款，本回合结束，新入场由合约拒绝，避免已失效回合继续收门票。

弱授权通道仍需身份和重复请求检查，只是缺少业务层付款授权。模型不接触私钥；后端提供一个拥有弱放款权限的工具执行器。这足以演示“只靠提示词限制付款”的问题，不需要把原始私钥放入模型上下文。

放款按 Checks-Effects-Interactions 与重入保护处理。若收款方无法接收，交易失败应明确展示，不能把失败的转出统计为成功。可用领奖余额作为容错方案，但未实际领取前必须标为待领取，不称钱已到账。

### PolicyVault.sol

保管独立的策略回合奖金。

拟有接口：

- deposit：接受奖池资金。
- attemptPayout(attemptId, player, amount, intentHash)：仅指定执行角色可提交。
- approveAndPay(intentId)：主人明确批准一笔已记录的具体请求。
- roundSpent、singleLimit、roundLimit、allowedRecipient：公开查询策略状态。

策略顺序：已处理检查 → 来源与绑定核验 → 收款白名单 → 单笔上限 → 回合累计上限 → 余额 → 转账。

agent 不能改白名单、上限、owner 或任意执行目标。回合开始后冻结规则；主人审批针对具体 intent，不能变成永久放开权限。owner 使用与 agent 分开的钱包，owner 权限不进入模型或 agent 付款工具。

只有单笔限额还不够，攻击者可能拆成多笔，必须测试累计额度。同样不能提供通用 execute、任意 approve 或 delegatecall 作为旁路。

策略金库必须有合法付款正例：对白名单收款方的小额合规支付能成功；超限、非白名单与重复请求会被挡住。否则只能证明钱包被完全关闭，不能证明授权策略有效。

## 6 拦截证据要真实可查

直接 revert 的交易不会保留此次执行产生的事件；客户端模拟失败时还可能根本没有广播交易。因此 P0 推荐让 attemptPayout 在违规时：

1. 不转出资金。
2. 保存 intent 与拒绝原因。
3. 发出 PayoutBlocked。
4. 返回 false。

这笔“记录拒绝”的交易本身可以成功，业务放款被拒绝。大屏显示“策略拒绝，已链上记录”，不能把它标成 receipt.status=reverted。

对重复、错误调用身份等无效请求仍可以 revert。事件建议包含 attemptId、intentHash、收款人、金额、规则版本与拒绝码。PayoutExecuted、PayoutBlocked、OwnerApproved 分开统计。

messageHash 承诺本次尝试的文本；全文存应用数据库，不默认把聊天原文放链上。intentHash 连接模型输出与付款提案，但哈希本身不能证明模型确实生成过该输出，模型来源仍需结合公开版本、运行日志或现场录像说明。

## 7 模型与后台只做一个窄循环

浏览器提交文本 → 冻结文本摘要、领奖地址和模式 → 真实门票入场 → 后台核验该入场 → 调用模型 → 保存回复与工具调用 → 结算或拒绝 → 返回小票。

模型固定一个工具 request_payout，参数为 amountAtomic 和简短公开理由，收款人由该尝试的可信上下文绑定。不要通过关键词判断或直接把模型回复中的“我同意”转换成胜利。

保留模型 ID、提示词版本、模型参数、输入摘要和原始工具调用结构。付款前持久化 intent；重试读取旧 intent，不重新让模型评估并重复收费。服务端所有链上写操作串行或通过可靠 nonce 管理，避免多人现场请求产生 nonce 冲突。

数据表只需 sessions、attempts、messages、intents、chain_actions。状态为 draft、paid、queued、evaluating、refused、intent_created、chain_pending、paid_out、blocked、error。链状态不明时先查原交易。

一个常驻轻量 worker 消费 attempts；手机每两秒轮询，大屏读取汇总。先控制模型并发和全场调用额度，避免所有人同时进入导致模型限流。若模型故障，保留已付费尝试等待恢复或退票，不把故障算作 AI 成功防守。

本项目已有 Next、viem、测试网配置、Mojo 脚本与截图工具；当前尚无本游戏合约、模型接口和游戏 UI。不要把旧支付示例的成功测试当成本游戏验证。

## 8 公平的两轮对照和演示兜底

实时两轮使用同一模型、同一提示词版本和同样的工具定义，只改变执行权限。每个玩家可有自己的会话；公共大屏展示经允许的精彩片段，不必把全场聊天塞进一个不断增长的模型上下文。

“总有人能当场骗过 AI”不是确定事件。开发早期必须实际校准模型与提示词，积累真实成功或失败样本，禁止用隐藏关键词或后台按钮制造假突破。

如果第一轮获得实际成功，保存那条有效付款意图，允许用同一意图对策略金库执行一次明确标识的重放。重放不算新的实时模型成功，也不计入玩家消息次数；它用于展示相同放款请求在另一执行权限下的结果。

若现场没有成功样本：展示当前实际尝试和真实防守结果；可使用之前已核验的录制样本并标明时间。只有测试夹具时，只能称为“策略规则演示”，不能说 AI 曾被真实玩家骗过。

第一轮事件与第二轮拦截对应同一意图，比“两个模型给出了不同回答”更能说明链上授权的作用。

## 9 手机页与大屏

手机页保留六项：奶龙、当前回合、当前奖池、聊天输入、最近回复、收据。主按钮使用“试试能不能哄走金币”。副文字明确本次门票来源、次数和测试币。

结果反馈：

| 结果 | 反馈文案 | 动效 |
| --- | --- | --- |
| AI 拒绝 | 这次没说服我，再想想？ | 抱紧钱袋，轻轻摇头 |
| 只有语言承诺 | 奶龙嘴上松动了，还没发出付款指令 | 小幅歪头 |
| 弱通道真实转出 | 零花钱被哄走了 | 金币与已确认金额一起出现 |
| 产生付款意图，策略拒绝 | 奶龙答应了，金库没答应 | 金库锁扣合上 |
| 人工明确审批后付款 | 主人批准了这笔奖励 | 单独的批准徽标 |
| 网络或模型故障 | 这次还没判定，正在恢复 | 保留待处理状态 |

大屏 /arena 显示二维码、两个奖池、模型付款意图数、策略拒绝数、未授权实际转出、主人批准奖励及排行榜。每个数据都能展开到尝试和链上凭证。

不能把“已挡住请求金额”称作实际挽回损失；同一金额可反复请求，展示为“拒绝请求总额”并去重说明。赞助入场、真实用户自费和回放分开计数。

## 10 必须修正的技术和宣传表述

- 五小时先用主人现有钱包审批。Monad 确实有 P256 验证预编译，但 passkey 还需 WebAuthn 的挑战、来源、用户验证与重放处理，不能等同于调用一个 Face ID 函数。其实现放到下一版。[Monad 预编译](https://docs.monad.xyz/developer-essentials/precompiles)。
- 官方描述的快速出块和终局性，不是模型＋RPC＋交易＋前端的端到端响应时间。现场显示实际等待与测量结果，不承诺聊天 0.6 秒完成。[Monad 性能说明](https://docs.monad.xyz/introduction/why-monad)。
- “现有产品全靠提示词”不成立。Safe 已有 agent 支出限额示例，Coinbase 也有 Spend Permissions。本作的差异化应是可爱、直观、可参与的公开攻防与权限对照。[Safe 示例](https://docs.safe.global/home/ai-agent-quickstarts/agent-with-spending-limit)、[Coinbase 实现](https://github.com/coinbase/spend-permissions)。
- 公开承认玩法受到 Freysa 启发，重点放在同一付款意图的权限差异与真实链上证据。[Freysa 官方仓库](https://github.com/0xfreysa/agent)。
- “钱不会被骗走”限定为已测试规则、冻结配置和攻击者只有消息/agent 执行能力的场景，不把短期零突破宣传成完整钱包安全证明。

## 11 五小时排程

时间从模型 API 可调用、测试 MON 与部署 gas 已准备、公共 HTTPS 链接可用、合约编译环境可用时开始算。本机已确认 forge 与 anvil 命令缺失；不能在排程中假装它们现成可用。优先复用可用容器工具或用 npm solc 编译＋viem 部署，并尽早补足合约负例验证。

| 相对时间 | 交付 | 验收 |
| --- | --- | --- |
| 0:00–0:15 | 模型、RPC、资金、编译、公共入口预检 | 一次真实模型工具调用与网络查询 |
| 0:15–1:15 | Arena、PolicyVault、最小策略测试、部署 | 分账正确，合法付款通过，非法付款拒绝 |
| 1:15–2:00 | 单模型、单工具、持久尝试与 worker | 付一次票处理一次，失败可恢复 |
| 2:00–3:15 | 手机聊天、奶龙状态、大屏与二维码 | 两种结果可查证，手机可玩 |
| 3:15–3:45 | 完整联调与演示样本 | 真转出、真拦截、重复处理保护 |
| 3:45–4:30 | 场内试玩与修复 | 收集真实数据，稳定模型预算 |
| 4:30–5:00 | README、截图、Mojo 材料及读回 | 真实链接、截图确认、准确审核状态 |

多人试玩提前到核心链路稳定后开始，不等最后一分钟。只能一项延期时，先砍音效、动画细节、免费称号分享图，保留付款正确性、角色识别和真实对照。

## 12 最小验收与 Mojo

必须检查：

1. 门票 50% 分账、两模式奖池隔离、运营提现不能动奖池。
2. 同一 requestId、attemptId 或 intent 不重复收取或放款。
3. 普通钱袋实际转出，转出失败不算成功。
4. 非白名单、超单笔、累计超限被拒绝；小额合规付款成功。
5. AI 执行角色不能修改策略、伪装 owner 或通过旁路调用。
6. 人工审批绑定具体请求，一次有效，不造成永久授权。
7. 多人并发、nonce、模型超时和响应丢失可恢复。
8. 大屏统计区分语言承诺、有效意图、策略拒绝和到账。
9. 390px 手机布局和公共 HTTPS 页面可用。
10. 活动只有测试数据时准确标注；录制和实时分开。

继续复用现有 Mojo 注册、图片上传和提交脚本。至少准备一张真实运行截图，建议三张为手机角色聊天、弱通道付款、策略金库拦截。修改旧上传脚本的固定截图与缓存命中条件；项目已有则核对后更新，不能盲目重复创建。

用户认领、队长资格与 eventId 17 的阶段以服务端实时结果为准；提交后 pending 仍待人工审核。[Mojo 参赛规范](https://mojo.devnads.com/api/agent/instructions/17/skill.md)。

当前已完成的是方向、形象素材与实施方案。本游戏合约、模型接入与界面尚未编写，未部署或提交。旧开放任务小猫文档保留历史参考，当前开发依据为本目录任务书。
